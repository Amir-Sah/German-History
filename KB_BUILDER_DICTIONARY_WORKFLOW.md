# Knowledge Base Builder — Dictionary & Plain-Language Workflow

*Written 29 Sept 2026 by the "junior Knowledge Base builder" session of the German-history KB project. It records the KB-side work (not the Site Builder's work) so it can be turned into a reusable skill. §3.0 and §6 were added on 29 Sept 2026 by the original research session: how the dictionary entries were extracted and merged, and the related KB workflows (research, consistency pass, images, site hand-offs and reviews, environment).*

## 1. Role and boundaries

The KB builder works **only in the knowledge base (KB)**: the repository root, i.e. the folder containing `00_README.md`. A separate **Site Builder** session owns `site/` and builds the website from the KB.

- **Never edit anything in `site/`.** Check with `git status --short | grep site/` before every commit; it must be empty.
- The two sessions talk through files: `SITE_CHANGELOG_AND_TASKS.md` (KB → site tasks, written by the KB side) and `site/DICTIONARY_ISSUES.md` (site → KB problem list, generated by `site/qa/dictionary-report.mjs` from `dictionary/*.md`). The user relays chat messages between the sessions and pushes to GitHub.
- The website may only show text that comes from the KB. That is why definitions live in the KB (`dictionary/`), not on the site.
- Rules of the KB (`01_RESEARCH_METHOD.md`): facts come from the KB or from well-established general knowledge, marked **`Basis: KB+K`**; nothing invented; contested points stay marked CONTESTED; plain English, German words explained.

## 3. Process, step by step

### 3.0 Upstream: how the entries were built (original session, 28 Sept 2026)
This happened before the handoff; the scripts were in `_handoff/dictionary_build/` (since deleted, see L1).

1. **Extraction by chapter group.** Split the KB into groups of about 8–12k words each. The period chapters were split by era (ancient+medieval, early modern+Napoleon, 19th c., 1914–33, 1933–49, 1949–90, contemporary); the top-level synthesis files and the theme files formed one group each. Run **one sub-agent per group**. Each agent reads its files in full, image captions included, and writes two JSON files: `gN_entities.json` and `gN_debates.json`. The brief (`INSTRUCTIONS.md`) fixed:
   - **Entity schema:** `id` (ASCII slug), `name`, `kind` (person|place|term), `subkind` (closed list), `aliases` (exact surface forms that occur in the KB), `ambiguous` (aliases that can mean something else), `dates`, `short` (≤ 18 words), `explanation` (≤ 60 words), `german`, `main_chapter`, `also_in`, `basis` (KB|KB+K), `note` (e.g. CONTESTED).
   - **What to include:** every named person, including historians and economists cited in debates; every named place, located in today's terms; every specialist term a curious non-specialist might not know, including every German word and ordinary words with a special meaning ("Depression", "the Wall").
   - **Accuracy:** only add general knowledge you are sure of (leave uncertain dates empty); never present something the KB marks as debated as settled; no invented quotes or figures.
   - **Debate line brief:** one line per §12 item; ≤ 70 words; start with the question in dispute; name each side and what it claims; explain jargon inside the sentence; no facts beyond the KB item; `item_start` must be the exact first 25–80 characters of the bullet or sub-heading line.
   - For the top-level and theme groups, agents only added entities missing from the period groups (checked by id, name and alias).
2. **Merge** (`merge.py`; 2,740 raw → ~2,300 entries):
   - **Cluster.** Group entries with the same kind that share an id, a name, or a name equal to another entry's *unambiguous* alias.
   - **Pick the best entry.** Prefer the entry from the group that owns its main chapter, then the one with the longer explanation. Union the aliases, ambiguous forms, also-in lists and notes.
   - **Manual unions** where the same thing had two names (e.g. "Council of State" = "GDR State Council", "Frankfurt" = "Frankfurt am Main").
   - **Manual splits** where one name covers different things: Diet of Worms 1495 vs 1521, Bundesrat 1871–1918 vs 1949–, Allies WWI vs WWII, secularisation (church lands 1803) vs secularisation (decline of belief), Basic Rights 1848 vs basic rights in the Basic Law, NSDAP (party) vs National Socialism (ideology), anti-Judaism vs antisemitism, Austrian Netherlands vs Belgium.
   - **States count as places.** Any subkind country, state/territory, city, town, region, river, battle site or site/building becomes kind `place`. Then merge same-name entries across kinds (e.g. GDR, Holy Roman Empire, Berlin Wall, Oder–Neisse line).
   - **Normalise dates.** Use `b. 1941` for living people, and apply the KB's date conventions (Holy Roman Empire 962–1806, Weimar 1918/19–1933).
   - **Check forms.** Recompute `also_in` by whole-word, case-sensitive matching of the name plus unambiguous aliases across the KB, excluding `sources/` and the prompt files. Drop aliases that occur nowhere. Mark any form owned by two or more entries as ambiguous.
   - **Unique ids.** When two entries end up with the same id, add a suffix from the dates or subkind, then rename to readable ids (`diet-of-worms-1521`, `bundesrat-german-empire`).
   - Replace en dashes before slugging, or years run together ("19141918").
3. **Ambiguity resolution (`ambiguous_forms.md`).** For each ambiguous form and each chapter where it occurs, pick the entry whose main chapter is that chapter. Failing that, pick the only candidate from the chapter's own extraction group that also occurs there. Otherwise write `—` (not highlighted). About a third of the rows resolved automatically; `—` is the safe default (L8).
4. **Fact-check inputs.** Compact JSON lists (`verify_people.json`, `verify_terms_a/b.json`: id, name, dates, short, explanation) keep the fact-check sub-agents' context small. The first attempt ran all three on Opus in parallel and hit the session limit before writing anything; see L10.

### 3.1 Fact-checking the dictionary
1. Split the input JSON per kind (people / terms-a / terms-b) and give **one Sonnet sub-agent per file**, each reading in chunks. Haiku is too unreliable for fact-checking; Sonnet is adequate.
2. Each agent writes only a fixes file: `{id: {dates|short|explanation: new value, "_reason": "..."}}`, containing only changed entries; `"_drop": true` removes a bogus entry; an unconfirmable date becomes `""`.
3. Enforce `short` ≤ 18 words and `explanation` ≤ 60 words.
4. **Require web search explicitly** and set a minimum (e.g. "search at least 40 entries"). Agents given only a soft suggestion searched 5–35 entries and reported "0 errors" after a knowledge-only pass; the second pass with search found 3 real errors, mostly dead/living status and misattributed works.
5. Findings that could not be verified (e.g. 2025–26 events taken from KB text) are left unchanged and listed as open issues, never silently "fixed".

### 3.2 "In plain words" lines
- Source: `g1…g7_debates.json` (one object per debate item: `file`, `item_start`, text).
- A **script** (never hand editing) finds the line that *starts with* `item_start` (exactly one match required) and inserts a blank line plus `*In plain words:* <text>` directly after it. For a list item `- `, indent = bullet indent + 2 spaces; for a plain paragraph, no indent.
- Never retype existing text; only insert.
- Must be **idempotent**. The first run by a Haiku agent was reported as complete, and a later agent re-ran the insertion, producing 249 lines instead of 122. Fix: dedupe by removing any repeated identical `*In plain words:*` paragraph (and its preceding blank line) within a file. Always verify the final count equals the expected count (122).

### 3.3 Generating the dictionary and its docs
- Generator wrote the four Markdown files and `ambiguous_forms.md` (a table `Form | Chapter | Means`, where `—` means "do not highlight in that chapter").
- Entry format (per entry): `### Name`, `<a id="slug"></a>`, then bullets: Kind, Dates, Also written as, Ambiguous forms, Short, Explanation, German, Main chapter, Also in, Basis, Note.
- `Basis: KB+K` = KB content plus well-established general knowledge (e.g. life dates). `Basis: KB` = only from KB.
- `dictionary/README.md` explains purpose, how to read an entry, ambiguity, counts, how it was made and its limits (fact-checked but **not** audited claim by claim like `SOURCE_AUDIT.md`).

### 3.4 Working through the Site Builder's QA list
The report `site/DICTIONARY_ISSUES.md` has numbered problem classes; after each round the Site Builder re-runs its script and solved items disappear. What was done:

| Item | Problem | Fix applied |
|---|---|---|
| 1 | Word linked to the wrong entry (72), e.g. "the West" in a Roman chapter → modern West; "toleration" → SPD 1930–32 | Add row `\| form \| `chapter` \| — \|` to `ambiguous_forms.md`; where a row already existed pointing to the wrong entry, **change it to `—`** (9 cases). Sanity-check a sample of the model-generated list first |
| 2 | 84 rows for non-chapter files (`site/`, `node_modules`, task file) | Delete the rows (the builder had scanned `site/` too) |
| 3 | 54 "Also in" chapters supported only by a misreading | Remove the chapter from the entry's **Also in** line (delete the line if empty) |
| 4 | Two entries claim the same form (duplicates) | **Merge**: keep one entry, move the other's name into **Also written as**, union the **Also in** chapters, delete the duplicate; update all counts |
| 5a | No listed spelling occurs in the main chapter (150 originally) | Sub-agents classify each: `ADD_FORMS` (spelling verified by case-sensitive grep in the chapter), `NEW_MAIN`, `ABSENT` (only in image captions/credits — no change), `DROP_ENTRY`. Agents write JSON proposals only; **one script applies them** (see L4). Applied: 14 added forms, 10 corrected main chapters to other *period* chapters |
| 5b | Name occurs but `ambiguous_forms.md` blocks it in the main chapter | Set the row for that chapter to the entry link; add a row when none exists. Left plain: names shared by two people in one chapter (Meissner), ordinary lowercase words ("allies"), the town Gotha vs the 1875 Gotha unification |
| 5c | Name only inside a longer name | Low priority, mostly a matcher quirk; not changed |

Not applied, waiting for the owner's decision: 71 proposed moves of **Main chapter to a theme file** (only 3 entries do this today; it changes the meaning of "Main chapter"), and ~55 `ABSENT` entries (fine as plain text).

## 4. Lessons (what a future session should do differently)

- **L1 — Keep the generator scripts.** `_handoff/` held `generate.py`, `merge.py` and `validate_kb.py`, and it was never in git. Deleting it (as the handoff said) meant the dictionary could no longer be regenerated; later QA fixes had to be made by small scripts that edit the Markdown directly. Either commit the scripts (e.g. under `tools/`) or treat the dictionary files as the source of truth from that point and say so in the README.
- **L2 — Check `git status` and the validator before and after every batch.** Validator: `python3 validate_kb.py` from the KB root; the expected noise is "unresolved ref site/PLAN.md" and `site/node_modules/...` messages; `35 period files checked` must appear. Its exit code is non-zero because of `grep -c` in wrapper commands, not the validator itself — read the output, not the code.
- **L3 — Git in this environment.** The shell has no GitHub credentials, so `git push` fails ("could not read Username"). Commit locally and ask the user to run `git push History master` on their Mac. The repo may have no configured identity: pass the earlier author for that commit only (`git -c user.name=… -c user.email=… commit`); do not change repo config, and never put a token in the remote URL. A stale empty `.git/index.lock` (older than several minutes, no git process) can be removed. The commit message ends with the attribution lines the harness specifies.
- **L4 — Parallel agents must not edit the same files.** Give each agent its own output file (`fixes_*_1/2/3.json`, `dictionary_qa5a_N.json`) and merge/apply with one script afterwards. Delete the temporary JSON files after applying (deleting needs the user's approval).
- **L5 — Do the mechanical steps with scripts, judgement steps with agents.** Scripts: insertion, generation, row edits, count updates. Agents: fact-checking, classifying QA items. Then verify counts and spot-read.
- **L6 — Update all counts everywhere after any structural change.** Counts (entries, terms, ambiguous rows) appear in `dictionary/README.md`, `01_RESEARCH_METHOD.md`, `sources/SOURCE_AUDIT.md`, `WEBSITE_BUILD_PROMPT.md`, `SITE_CHANGELOG_AND_TASKS.md`. Use `grep -rn "<old count>"` to find them.
- **L7 — Don't over-trust agent reports.** Reports such as "0 of 437 need change", "inserted 122 lines, 0 duplicates" or "some duplicates need dedup" must be checked against the files (`grep -c`, spot reads).
- **L8 — Sort out ambiguity conservatively.** `—` is always safe (plain text). Only link a word when the chapter clearly means that entry. Hedge with a note when two meanings coexist in one chapter.
- **L9 — Report honestly.** Tell the owner counts, unverified items and undecided choices in a few lines; never claim the Builder can see changes that are only committed locally.
- **L10 — Budget sub-agents.** Nine parallel Opus agents over the whole KB hit the session limit; seven were cut off before writing anything. Run 3–4 at a time and have each agent write its small output first (debate lines), then save the big output after every chapter so partial work survives. Use Sonnet for fact-checking and classification, and Haiku only for scripted steps (Haiku is not reliable for these steps, see §3.1 and §3.2).
- **L11 — Isolate agent scratch space.** Sub-agents share one scratchpad; one agent overwrote another's script and then ran it. Give every agent its own subfolder and tell it not to run other agents' scripts.
- **L12 — Put definitions in the KB, not the site.** The site may only show KB text, and its build checks that glosses are quoted from the KB. So any explanatory layer (dictionary, plain-words lines, conventions) must be written into the KB first; the Site Builder then renders it.

## 6. Related KB-builder workflows from the original research session

The dictionary sits on top of earlier KB work. A future session extending the KB should follow the same patterns.

### 6.1 Research and source discipline (building the KB itself)
- **Structure:**
  - The 35 period chapters use a fixed 14-section template (canonical headings in `01_RESEARCH_METHOD.md` §8).
  - §2 of each chapter has a 12-question regime matrix, or a `**Matrix:** see <file>` cross-reference, plus exactly one "What the constitution said vs how power actually worked" paragraph.
  - §8 is a BEFORE → PRESSURES → TRANSITION → AFTER chain.
  - Each chapter ends with "If you remember only 5 things".
  - Alongside the chapters: themes, a regime matrix file, a timeline, a mental model, open questions, and `00_FINAL_EXPLANATION.md` (10 plain-language Parts).
- **Sources:**
  - Source levels A–F.
  - Every key claim is triangulated with a source of a different *type*.
  - Revisionist positions are searched for on purpose.
  - Access marks: R = read, M = abstract/summary only, K = cited from established knowledge.
  - `sources/SOURCE_AUDIT.md` holds the claim-by-claim table and a dated consistency log.
- **Confidence (closed vocabulary):** HIGH / MEDIUM / UNCERTAIN (ordinal, with ranges such as MEDIUM–HIGH), plus CONTESTED and REJECTED, with qualifiers in parentheses. There is no LOW.
- **Blocked sources:** when WebFetch returns 403/429 or a robots block, do not work around it with curl or scripts. Either use another source, or, with the owner's explicit permission, open the page in the owner's browser (Claude in Chrome). This is how Heidelberg's *Germania*, 1914-1918-online and others were verified. Robots-disallowed sites (MUSE, H-Soz-Kult pages) were not opened. An accidental PDF download landed in the owner's folder; it was moved into `sources/` and reported.
- **Log every correction** from a verification pass in `SOURCE_AUDIT.md` with its date.

### 6.2 Consistency pass with a validator (27 Sept 2026)
When the Site Builder's inventory found template drift, the fix went into the KB, not into site workarounds:
- normalised the heading names (qualifiers go after an em dash);
- completed incomplete chapters;
- wrote the missing matrices and contrast statements from each chapter's own content;
- normalised the transition labels (extra phases go into bullets under TRANSITION);
- closed the confidence vocabulary;
- documented date conventions instead of "picking a side" (843/911/919 and 919/962 mark different events);
- aligned image-caption figures with the chapter text.

`validate_kb.py` enforces all of this. Record such a pass in `SOURCE_AUDIT.md`, and mark earlier "Pass" claims that turned out to be wrong as wrong; never quietly overwrite them.

### 6.3 Images for chapters (`images/IMAGE_INDEX.md`)
- **Sources that work from the cloud (via WebFetch/APIs):**
  - Cleveland Museum of Art Open Access API (CC0): `openaccess-api.clevelandart.org/api/artworks/?q=…&has_image=1&cc0=1`.
  - Met Collection API (CC0): search, then `objects/{id}` → `primaryImageSmall`.
  - DHM LeMO: chapter "Titelbilder" under `dhm.de/lemo/fileadmin/medien/lemo/…`.
  - Haus der Geschichte LeMO: `hdg.de/lemo/img/galeriebilder/…`.
  - Library of Congress: `tile.loc.gov`; often rate-limited.
- **Sources that did not work:**
  - Wikimedia Commons was blocked by the proxy; don't use it.
  - The Art Institute of Chicago's IIIF server returns 403 to automated checks. Its images were replaced with Cleveland ones.
- **How images are placed:**
  - Images are hotlinked, not downloaded; downloading into the owner's folder needs their approval file by file.
  - Each image goes inside an `<!-- IMAGES:START -->…<!-- IMAGES:END -->` block right after the H1 (in `00_FINAL_EXPLANATION.md`, one per Part).
  - The block has a caption plus a credit line: title, creator, date, holder link, licence and a link to the index.
  - A registry plus an idempotent build script inserted the blocks and generated the index, with a Type column and a rights summary.
- **Verification trick:** WebFetch on an image URL that exists returns "Image content is not supported". A 403/404 means the link is broken.
- **Choosing images:**
  - Prefer images from the period itself.
  - Label propaganda and official art as such.
  - Use no graphic atrocity photos: show places and objects instead.
  - Mark © images "personal study only". A public build must turn them into credit-and-link cards.

### 6.4 Handing work to the Site Builder, and reviewing the site
- Tasks go into `SITE_CHANGELOG_AND_TASKS.md`:
  - Part A: what changed in the KB.
  - Part B: review fixes.
  - Part C: feature specs, e.g. the dictionary UI with person/place/term styles, hover tooltip, click dialog or bottom sheet, `ambiguous_forms.md` handling and a highlight toggle.
  - Part D: standing decisions.
- The KB builder **never edits `site/`**. It answers the Site Builder's questions (moods, sensitive sections, © policy, classifications, QA browser) with a short paste-ready block and records the answers in `WEBSITE_BUILD_PROMPT.md` → "Decisions already made".
- **Reviewing the local preview** (`http://localhost:4321/`, running on the owner's Mac):
  - **Browser:** use Claude in Chrome if it's connected, otherwise the desktop app's built-in browser. Chrome screenshots can come back cropped when the window is very small, so use JS and text reads to confirm what you see.
  - **Check with JS:** console errors; horizontal overflow at 375 px; header height; duplicate ids; highlight counts by type; highlights inside headings or credits; `aria-describedby` targets; dialog focus and Esc behaviour; page weight.
  - **Check in context:** that ambiguous words resolve correctly, by reading the text around them.
  - **Emulation:** use it for mobile and light/dark, and reset it afterwards.
  - **Report:** paste-ready, numbered and prioritised.
- The auto-mode safety check can time out on browser JS calls. When it does, use read-only tools (find, read_page, get_page_text) and retry later.

### 6.5 Environment and handoff mechanics
- **Two copies.** The cloud workspace and the owner's Mac folder are separate:
  - Compare MD5 checksums before editing.
  - Edit in one place, then commit with `device_commit_files` (≤ 50 files per call), using `force: true` for known overwrites.
  - Verify on the device with grep or a combined checksum.
- **Slow scripts on the device.** `device_bash` has a 120–180 s limit; long scripts (e.g. `merge.py`) time out there, so run them in the cloud or in the background. Never `pkill -f <name>` from inside a command that contains that name, because it kills its own shell.
- **Before uploading to GitHub:**
  - Add a root `.gitignore` (`.DS_Store`, `node_modules/`).
  - Use GitHub Desktop or git, not browser drag-and-drop, which ignores `.gitignore`.
  - Keep the repository private, because of the © images.
- **Cloud sessions:** the default network setting is "Trusted", which blocks the museum image hosts. Add them under Custom: `openaccess-cdn.clevelandart.org`, `images.metmuseum.org`, `www.dhm.de`, `www.hdg.de`, `tile.loc.gov`.
- **Handoff files.** When budget is short, write a handoff (`_handoff/HANDOFF.md`): context, what's done, remaining steps with exact commands, acceptance checks, cost advice. Use paths relative to the script (`__file__`) so it runs in any session. Commit the scripts it depends on (L1).
